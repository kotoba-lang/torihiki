## 方法 (いずれもリポジトリ内コード変更なし)

- fuzz-seeded.cljc をインメモリで n-seeds=80 に伸長して実行:
  - JVM: `clojure -M -e '(load-file "evidence/fuzz-seeded.cljk") (in-ns (quote fuzz-seeded)) (def n-seeds 80) (run)'`
    → evidence/fuzz80-jvm-2317.out (85 行, 80 seed 完走)
  - nbb: driver `evidence/fuzz80-driver.cljk` を
    `nbb --classpath "$(nbb script/nbb-classpath.cljk)" evidence/fuzz80-driver.cljk` で実行
    → evidence/fuzz80-nbb-2322.out (82 行, 80 seed 完走)
- nbb 側の実測済み罠 (今回初めて machine に記録):
  1. nbb の `-e` コンテキストに `load-file` も `slurp` も無い
     (evidence/fuzz80-nbb-2317.err / -2320 以前の err)。`load-string` + fs.readFileSync で回避
  2. nbb の `load-string` は新規 namespace の require を解決できない
     (`Could not find namespace torihiki.state`, evidence/fuzz80-nbb-2318.err) → driver 側で事前 require
  3. driver 内の `(in-ns 'fuzz-seeded) (def n-seeds 80)` は nbb で無視される
     (16 seed のまま走った: evidence/fuzz80-nbb-2321.out, 18 行)。
     `(alter-var-root #'fuzz-seeded/n-seeds (constantly 80))` が正解

## 実測 (verdict)

- **JVM==nbb: 全 80 seed で seed 行 byte-identical**
  (`grep '^seed' | sort | diff` → 差分ゼロ。evidence/fuzz80-jvm-2317.out vs fuzz80-nbb-2322.out)
- **pin 済み 16 seed は歴代 digest と完全一致** (fuzz-jvm-2311.out の seed 0..15 と diff ゼロ) —
  つまり 9 度目の pin 再確認でもあり、かつ **未実測 seed 16..79 の 64 個でも等しい**
- 全 80 seed で snapshot round-trip parity flag = `true` (mid-fold capture/restore の
  flat root / state root が全 seed で一致)

**→ H4 は反証された (falsified)。** cross-runtime digest 一致は pin の外側 64 seed でも成立。
