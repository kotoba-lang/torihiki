# engine-rs — stage-1 single-threaded matching engine (AWAI-3556)

A Rust reimplementation of the torihiki matching layer: price-time priority
limit order books, integer prices and quantities, deterministic state
hashing, and an Ed25519 authentication boundary whose verification is
separable from matching.

The existing Clojure-family implementation (`src/torihiki`,
`lib/kotoba.torihikiCore`) is the **oracle** for matching decisions. This
crate replaces nothing and edits nothing there; it mirrors the oracle's
matching rules and proves it with fixtures generated by running the oracle
(see `evidence/`).

## Scope

In scope (stage 1):

- Per-market limit order books: new order, cancel, fills (full and
  partial), integer prices and quantities, explicit overflow handling,
  bounded memory per order (`Book::new(n_levels, cap)` preallocates every
  slot and level queue; no per-order slab allocation — the fills returned
  to the caller are bounded by the depth of the book that already exists,
  and hashing/market-listing walks allocate scratch proportional to the
  resting state).
- Deterministic matching: the same input sequence yields the same state
  hash. Determinism rules: ordered maps/sets only (`BTreeMap` markets,
  `BTreeSet` occupied levels), order ids from slot arithmetic, no hash-map
  iteration anywhere near the hash or the output, integer arithmetic only.
- Order authentication boundary: orders and cancels carry Ed25519
  signatures (`auth::SignedOrder` / `SignedCancel`); the engine rejects what
  does not verify. Verification is separable — `Engine::apply_signed_order`
  verifies then applies, while `Engine::apply_order` applies a pre-verified
  order, so a later stage can verify a block's signatures in parallel and
  replay the verified orders through the single-threaded matcher. The bench
  measures both paths.
- Negative controls and property tests (see below).

Out of scope (later stages, explicitly not built here):

- Parallel signature verification — the seam exists
  (`verify` vs `apply_*`); the parallel scheduler does not.
- Persistence, snapshots, BFT/consensus, validators, real funds.
- Everything above matching: margin, positions, reduce-only clamping
  against a position, fees, funding, mark prices, triggers/TWAP/scale,
  oracle prices, clearinghouse, nonces and replay protection, key binding
  and agent keys. The reduce-only flag bit is accepted and ignored by the
  book exactly like the oracle's book; clamping it is the clearinghouse's
  job (`torihiki.state/apply-tx :order` forces IOC on reduce-only and never
  lets it rest — a stated oracle difference from Hyperliquid).
- Amend (`reduce-to!` / cancel-and-replace): out of scope for stage 1. The
  oracle behavior is recorded in `evidence/oracle-runs.md` and stays
  unimplemented here.

| Concern | Oracle | This crate |
|---|---|---|

| Order/cancel shape doors | `torihiki.api/validate-order-shape`, `order-tx-shape`, `cancel-tx-shape` | `domain::validate_order_shape`, `Engine::apply_order` / `apply_cancel` door order |

## Matching rules mirrored (with oracle sources)

- Price-time priority: resting orders queue FIFO per level; a taker sweeps
  the best opposing level first, then outward
  (`torihiki.book/place!` loop, `best`, `level-orders`).
- The fill price is always the maker's level; fills consume the queue head
  first (`emit-fill!` records `bl`, the maker's level — the taker's limit
  never sets the price, so there is no rounding anywhere).
- Full and partial fills; the remainder rests unless IOC, post-only
  refused, or the slab is full (`place!` returns -1 for all four; this
  crate returns `oid: None` with whatever fills happened).
- Post-only that would cross rests nothing and emits no fills
  (`post-only-rejects-a-taker`).
- Full book takes what crosses and rests nothing, like an IOC
  (`take-slot!`); the apply door refuses a *resting-only* order on a full
  book that cannot cross with `:book-full`
  (`torihiki.api/validate*` `:book-full` clause, `marketable?`).
- Cancel compares owners and answers nothing cancellable with 0: unknown
  id, filled order, stale generation, wrong owner (`cancel!` requires
  `owner`; `stale-id-cannot-cancel-a-stranger`).
- No self-trade prevention: a taker fills its own resting orders like
  anyone else's. The oracle has none either (verified by searching the
  oracle sources for self-trade/wash handling — none exists; pinned by the
  `self-trade-fills-own-order` fixture).
- Validation order and taxonomy: unknown-market, then bad-account (any i53
  integer, negatives included — `torihiki.auth/account-ok?`), then side,
  quantity (`1..=2^53-1`), price level (`0..n-levels`), notional
  (`qty > i53-max/level`, division so the check itself cannot overflow),
  flags (`0..=7`), and at apply time book-full
  (`torihiki.api/validate-order-shape`, `validate*` `:order`/`:cancel`
  clauses). IOC = 1, post-only = 2, reduce-only = 4 (ignored by the book).
- Conservation: `submitted = 2*filled + resting + cancelled` — each fill
  consumes one lot from a taker and one from a maker (the oracle's
  `conservation-of-quantity` equation, mirrored exactly).

## Deliberate deviations from the oracle

1. **Cancel of a non-cancellable id is an explicit rejection, not a silent
   no-op.** The oracle's `cancel!` returns 0 for unknown, filled,
   already-cancelled, stale, and wrong-owner ids, and `apply-tx :cancel`
   leaves the state unchanged. This engine returns
   `Rejection::UnknownOrder`, or `Rejection::NotOwner` when the id names a
   live order of another account. Same state effect (nothing changes, hash
   unchanged), louder surfacing — the task requires double-cancel and
   unknown/filled-cancel rejections as negative controls.
2. **The state hash commits to matching-engine state only** (books), not to
   clearing, nonces, rejections, governance, or other sections. Rejections
   in particular are excluded on purpose: a rejected order must leave the
   state hash unchanged, which the parity and negative tests assert.
3. **Order ids are part of the hashed state** (slot + generation per
   resting order). The oracle deliberately excludes ids from its root and
   keeps cancel semantics consistent across restores via snapshot
   generations plus `:rejected` entries. Stage 1 has no snapshot/restore
   yet; hashing the slots is the simpler total rule. Documented here so a
   later snapshot design knows what it is replacing.
4. **The signature payload is engine-scoped, not the chain envelope.** It
   covers market, account, side/level/qty/flags (or market/oid/account for
   cancels) under a `torihiki-eng/v1` domain separator, field-per-line like
   the oracle's `signing-payload`. It is NOT byte-compatible with
   `torihiki.auth/signing-payload` (no chain id, no nonce) and carries no
   replay protection — nonces are later-stage state.
5. **Occupied-level lookup is an ordered set per side, not the oracle's
   four-level bit ladder.** Same answers (`best`, `next-occupied`), same
   determinism (iteration in level order only), different structure.
6. **No fill event buffer with a cap.** Fills are returned to the caller of
   the order that produced them; per-call memory is bounded by the book
   that already exists. (The oracle's `ev-cap` buffer exists because fills
   cross a block boundary into settlement; stage 1 has no settlement.)

## State encoding

`hash::canonical_bytes`, hashed with SHA-256, hex-encoded lowercase (the
same digest the oracle's `flat-root`/`state-root` use; different bytes —
see deviation 2).

- Integers encode as the oracle's `enc-int`: a sign byte (0/1) then seven
  big-endian magnitude bytes (division-based, exact on every platform).
  `enc_int` is unit-tested against the oracle's byte form, including
  `2^53-1 = [0, 0x1F, 0xFF×6]`.
- Layout, all sections tagged (tags mirror `torihiki.state/enc-tag-*`
  where the section exists there: exchange = 1, market = 2, level = 3,
  order = 4):
  - `[1, market-count]`
  - per market in ascending id order: `[2, market-id, n-levels]`
    - per side (bid 0, then ask 1): `[2, side, occupied-level-count]`
      - per occupied level, best-first (bids descending, asks ascending):
        `[3, side, level, level-qty, queue-length]`
        - per resting order in time (queue) order:
          `[4, slot, generation, owner, qty]`
- Iteration is over sorted market ids and best-first levels — never over an
  unordered map. Two engines that applied the same sequence reach
  byte-identical encodings; any rejection leaves the bytes (hence the hash)
  unchanged.

### Bench

`cargo run --release --bin bench` — single-threaded, deterministic LCG tape
generated before the clock starts, mix mirroring the oracle bench (43%
cancel / 12% aggressive cross / 45% passive quote, owner = index & 1023,
cancels aimed at a ring of recent placements so slots turn over), with the
oracle's refusal rule (exit 1 when no cancel succeeded). Two paths: `match`
(no crypto) and `verify` (every order and cancel Ed25519-verified;
signatures produced once up front, untimed — the clock covers verification
+ matching only).

Machine (all runs): Apple M1 Max, macOS 26.4, 10 cores, 32 GB RAM,
`rustc 1.99.1`, release profile (`opt-level 3`, thin LTO). The machine was
under heavy load (load average 26–35 on 10 cores from concurrent agent
sessions — same caveat the oracle README records about its own figures),
so treat absolute numbers as machine-noisy; the A/B (match vs verify) ran
back to back on the same machine.

|---|---|---|---|---|---|---|

| steady-state 43/12/45 | 3,000,000 | 1 | verify | 177.0 s | **16,954 ops/sec** (58,984 ns/op) | 352,903 |

Full logs: `evidence/bench-*.txt` (each prints mix, ops, placed,
cancelled, fills, resting, state hash, elapsed, ops/s, ns/op).
The 3M match row is an independent re-run from the review: same tape,
same counts (1,350,766 placed / 774,347 cancelled / 548,630 fills),
hash `e84216…` identical to the 3M verify log. The absolute rate moves
with machine load (6.8–10.3M ops/s across two 3M runs minutes apart),
which is why the table keeps the load caveat.

Reading the table:

- The stage target (~1,000,000 order ops/s single-thread) is met by the
  matching path with headroom: ~15M ops/s saturated, ~16M unsaturated on
  this machine — but note the caveat above about load noise, and that the
  long match runs saturate the 2M-slot book (growth ≈ 75k resting per Mops;
  after ~1.5 s the mix measures a saturated book: non-crossing news refused
  `:book-full`, crossing news still filling). The unsaturated reference row
  is the steady-state figure; the 30 s rows are the required sustained
  runs, reported with their saturation stated.
- With verification included, throughput is ~17k ops/s — the Ed25519
  verifies (~59 µs each here) dominate ~900:1. That gap is the reason the
  auth boundary is separable: a later stage must verify in parallel.
- The 3M-op verify run and the 3M-op match run print the SAME state hash
  (`e84216…`), cross-confirming that verification changes nothing about
  matching. Both logs are in evidence (`bench-verify-1mkt-3M.txt`,
  `bench-match-1mkt-3M.txt`); the match side was re-run independently
  during review and reproduced the hash and all four counts exactly.
- 4 markets run slower per op (108 ns vs 66 ns): four ~100 MB books exceed
  cache, and per-op market dispatch is no longer free. Still 9× target.

## What is unverified

- Absolute bench numbers under load noise (see above); no quiet-machine
  re-run was done. Relative statements (match vs verify, saturated vs
  unsaturated) ran back to back and are the trustworthy part.
- `cargo clippy` could not be installed via `rustup` (sandbox blocks its
  download scratch and `~/.rustup` writes), so the gate ran with a
  version-matched clippy 1.99.1 unpacked from
  `static.rust-lang.org/dist/2026-10-15` into a hardlink-free copy of the
  local toolchain under `/tmp`. Same binary version as the local
  `rustc 1.99.1`; the workaround is environment-only, not a code change.
- The oracle's JVM leg was not run (its `clojure -Spath` resolution needs
  `~/.gitlibs` worktree writes, blocked here); the oracle ran on its SCI
  (`kbb`) leg instead, which is the leg the repository deploys
  (torihiki-node compiles the engine to a Worker bundle) and whose suite
  must match the JVM leg exactly.
- No networked, multi-producer, or adversarial-clock behavior was tested:
  stage 1 is a single-threaded function of (state, inputs).
